# Pre-flight review: requs.md §7 restructuring plan, final adversarial pass

Reviewed 2026-08-08, against `requs.md:474-614` and the sources of all repositories in scope on this machine. Scope per commission: what is new or changed since `reviews/ocp-viewer-architecture-review.md` (2026-08-07, verdict go) and `reviews/ocp-viewer-coverage-audit.md` — the two new packages, the retirement of `python -m ocp_vscode`, ocp_tessellate 3.5.0, the version matrix, the no-OCP-provider rule, the six-step order, and the module layout rule. Prior findings are not re-litigated; I spot-checked that they are folded in (they are: the sixteen-named-functions correction at requs.md:577, the Comms vocabulary and `send_data` handle at :567-569, the generated widget lists at :593, the spot-checked hedge at :523, animation in both shared columns at :514) and found no regression against the audit.

## Verdict

**Go, with three majors to fix in the plan text before step 1 and one release to add to the order of work.** The architecture is unchanged from the reviewed one and remains sound; the new structural decisions are mostly right and two of them are verified stronger than the plan claims: the PyPI names `ocp-viewer` and `ocp-viewer-core` and the npm name `ocp-viewer-core` are all unclaimed (404 on both registries, checked 2026-08-08), and the irreversible, user-breaking changes (entry-point retirement, dependency drops, branch deletions) are correctly sequenced at step 5, after two adoptions would have revealed a wrong interface, while everything before them is additive. The three majors: the plan retires `python -m ocp_vscode` as "the old standalone entry point" when it is also the entry point the VS Code extension itself spawns for the measurement backend (`src/controller.ts:324`); the version matrix creates a window (steps 3-5) in which `ocp_viewer` cannot be pip-installed into any environment containing ocp_vscode ≤4.x — which is every environment a current standalone user has — and the plan calls that window "harmless"; and the module layout rule (`config`, `codec`, `comms` import no OCP) is unachievable against today's imports without either tessellate work the plan does not schedule or an interface decision (where BRep serialization for the backend channel lives) the plan does not make. None of these invalidates the design; all three would be discovered mid-flight at the worst possible time if not written down now. Counts: 11 findings (3 major, 4 medium, 4 minor), 15 public surfaces touched of which 2 break silently as planned and 2 are unaddressed, 6 could-not-verify items.

## Findings, ranked by risk to the restructure

### F1 (major). `python -m ocp_vscode` is not only the standalone's entry point — the extension spawns it for the measurement backend, and the plan retires all of it

**What the code does.** `ocp_vscode/__main__.py` is one click command with three behaviours: `--create_configfile` writes `~/.ocpvscode_standalone` (`__main__.py:364-368`), `--backend` starts the measurement `ViewerBackend` (`__main__.py:370-384`), and the default starts the standalone viewer (`__main__.py:386-388`). The VS Code extension itself spawns the second one by name: `"${python}" -m ocp_vscode --backend --port ${this.port}` at `vscode-ocp-cad-viewer/src/controller.ts:324`. Version skew between extension and wheel is a warning, not a stop: `src/extension.ts:60-80` compares semver and shows a message (newer wheel → error toast, older wheel → an offer to install), and the quickstart/install templates use compatible-release ranges, `ocp_vscode~={ocp_vscode_version}` (`package.json:556,559,578`). There is no `[project.scripts]` entry in `vscode-ocp-cad-viewer/pyproject.toml` — `-m` is the only CLI surface, so `__main__.py` is exactly the retirement target, but it is a shared one.

**What the plan says.** "this is where the old standalone entry point retires" (requs.md:603); "`python -m ocp_vscode` prints and stops rather than forwarding … Printing lets ocp_vscode shed flask, flask_sock, click, questionary and pyperclip outright" (requs.md:583); the notice "is **scoped to the standalone**" (requs.md:583). Nowhere in the section do `--backend` or `--create_configfile` appear, and nothing says the extension's spawn command changes.

**Assessment.** Executed as written, step 5 breaks its own extension: dropping click removes the parser, the new `__main__` prints the standalone migration notice and exits non-zero, and the extension's backend spawn dies with a message about a product the user is not running. The same-release coupling (bumpversion ties `pyproject.toml`, `src/version.ts` and `package.json`, `vscode-ocp-cad-viewer/pyproject.toml:91-109`) means the fix is cheap — but only if the plan names it, and the stale-combination case (extension 4.x with wheel 5.x, reachable because the version check only warns) leaves a user with a dead measurement backend whose only symptom is one stderr line in a terminal they rarely read. Change: item 14/step 5 must state (a) where the backend's process entry point moves — it belongs beside the backend itself, which item 5 puts in `ocp_viewer_core`, so something like `python -m ocp_viewer_core.backend --port N`, parsed without click; (b) that `controller.ts:324` changes in the same release; (c) that the migration notice checks `sys.argv` for `--backend` and prints the backend-specific message (pointing at the extension upgrade) rather than the standalone one; (d) what happens to `--create_configfile` (see F10).

### F2 (major). The version matrix makes `ocp_viewer` uninstallable beside ocp_vscode ≤4.x — the exact environment every current standalone user has — for the whole steps 3-5 window

**What the code does.** ocp_vscode 4.0.1 declares `ocp-tessellate>=3.4.0,<3.5.0` (`vscode-ocp-cad-viewer/pyproject.toml:30`). The matrix (requs.md:533) has `ocp_viewer_core 1.0.0` declare `ocp_tessellate >=3.5.0,<3.6.0`. The ranges are disjoint, so a resolver refuses any environment containing both ocp_vscode ≤4.x and anything that depends on the core — which after step 3 is `ocp_viewer`, the package the standalone user is being asked to move to. The standalone ships inside ocp_vscode today and is documented that way (`README.md:130`: "Standalone mode allows you to use OCP CAD Viewer without VS Code: `python -m ocp_vscode`"), so the population that wants `pip install ocp_viewer` first is precisely the population whose environment already has ocp_vscode. jupyter-cadquery environments inherit the same ceiling transitively until step 6 via `ocp_vscode~=4.0.1` (`jupyter-cadquery/pyproject.toml:33`).

**What the plan says.** "Between steps 3 and 5 the standalone exists twice, which is harmless but must not be left ambiguous" (requs.md:603); "a 3.5.0 is refused by today's ocp_vscode, there is no second ceiling to find, and the whole coordination is one line in the release that adopts it" (requs.md:547), presenting the ceiling's refusal purely as a benefit.

**Assessment.** The refusal has two directions and the plan only prices one. Refusing old-core-with-new-tessellate is the intended hygiene; refusing new-core-*beside*-old-ocp_vscode blocks the migration path for the standalone's own users during the window in which the plan wants them to migrate. Because item 0 is genuinely additive (parameters defaulting to today's globals, requs.md:547), ocp_vscode 4.x runs fine on tessellate 3.5.0 — the ceiling is a guess made before 3.5.0 existed, not a real incompatibility. Change: add to the order of work, between steps 1 and 3, an ocp_vscode **4.x patch release that widens the tessellate ceiling to `<3.6.0`**, published after 3.5.0 passes ocp_vscode 4.x's tests; that single release opens coexistence for the whole window. Alternatively, state explicitly that `ocp_viewer` cannot coexist with ocp_vscode until step 5 and make the step-5 migration notice the first moment anyone is told to install it — but that forfeits step 3's "first thin host proves the layering with real users" value, so the patch is the better answer.

### F3 (major). The module layout rule — `config`, `codec`, `comms` import no OCP — is contradicted by today's imports in two ways the plan does not resolve

**What the code does.** First: `ocp_vscode/comms.py` imports OCP-touching symbols at module scope — `from ocp_tessellate.ocp_utils import is_topods_shape, is_toploc_location, serialize, loc_to_tq` (`comms.py:31-36`) — and its default wire serializer base64-encodes BRep geometry via `serialize` (`comms.py:99-101`). That is not an accident to delete: the backend channel's payload *is* OCP geometry (shapes sent for measurement), so under the rule someone other than `comms` must serialize it, and the plan never says who. Second: the OCP-free half cannot import *anything* from the ocp_tessellate distribution, because `ocp_tessellate/__init__.py:39` does `from .ocp_utils import is_cadquery, occt_version`, and `ocp_utils.py:26-38` imports OCP at module scope — so `from ocp_tessellate.utils import Color` (`ocp_vscode/config.py:34`) and `from ocp_tessellate.utils import Timer` (`comms.py:30`) each pull the whole kernel today. The plan itself relies on this rule being cheap: "Splitting `config`, `codec` and `comms` from `tessellate` and `backend` needs no lazy imports at all - each module simply imports what it uses, at the top, and the OCP-free half is importable because nothing in it reaches for OCP" (requs.md:563).

**What the plan says.** Besides requs.md:563 quoted above: "the split is **detectable**: if the config merge or the wire format cannot be imported without geometry, then one of them has quietly acquired a dependency on it" (requs.md:561).

**Assessment.** The rule is right and worth keeping — but as of today the config merge *cannot* be imported without geometry, through two routes, and fixing the second route means either (a) ocp_tessellate 3.5.0 also lightens its package `__init__` so that `ocp_tessellate.utils` is importable without OCP — additional scheduled work for item 0, and it must be done additively because `is_cadquery`/`occt_version` are re-exported at the root and `ocp_vscode/show.py:29` imports `OcpGroup` from the root — or (b) the core vendors `Color` and `Timer` (both are small, OCP-free classes that merely live in an OCP-importing distribution). Change: item 0/step 1 gains the `__init__` lightening (or item 5 gains the vendoring decision), and item 7 or item 5 states where the backend channel's BRep serialization lives under the rule — the natural answer is the `backend` module owns serialize/deserialize and hands `comms` opaque bytes, which also matches "ocp_tessellate produces arrays, `ocp_viewer_core` decides the wire format" (requs.md:570).

### F4 (medium). `import ocp_vscode` silently enables the native tessellator — the plan's "eight lines of re-export" has no owner for that side effect

**What the code does.** `ocp_vscode/__init__.py:34-52` tries to import `enable_native_tessellator` and enables it unless `NATIVE_TESSELLATOR=0`, printing "Found and enabled native tessellator." Every host that imports ocp_vscode gets this today; jupyter_cadquery gets it transitively.

**What the plan says.** Hosts become "a `Comms`, a settings source, about eight lines of re-export" (requs.md:514); the core's "`__init__.py` stays import-free" (requs.md:557).

**Assessment.** If the enablement lands nowhere, every host silently falls back to the Python tessellator — no error, no missing function, just slower shows, which is the kind of regression nobody attributes correctly for weeks. It cannot live in the core's `__init__` (import-free by decision) and should not be a host duty times four. Change: item 5 names the owner — the natural home is the core's `tessellate` module at import time, keeping the `NATIVE_TESSELLATOR` env var; the print should become quieter or once-per-process, but that is taste, the ownership is the requirement.

### F5 (medium). ocp_tessellate 3.5.0's "convert tail stops encoding" is a breaking change to a documented public API, and step 1's ordering rationale for it is a false dependency

**What the code does.** The tessellate-internal encode at `ocp_tessellate/convert.py:2105` sits inside `export_three_cad_viewer_js` (`convert.py:2071`), a documented public function — `ocp-tessellate/README.md:44` shows it imported and `:57` documents it as "The direct integration point with three-cad-viewer". No repository in the ecosystem calls it (grep over all eight projects finds only the definition, the README and the CHANGELOG), so it is exclusively external-user surface. The shared show path's encode is a different site entirely: `ocp_vscode/show.py:537` calling `numpy_to_buffer_json` — nothing on the show path goes through `convert.py:2105`.

**What the plan says.** "The encoding is applied in two places … `ocp_vscode/show.py:537` calls `numpy_to_buffer_json`, and so does ocp_tessellate itself, in its own convert tail at `ocp_tessellate/convert.py:2105`. Both have to stop" (requs.md:570); step 1: "ocp_tessellate **3.5.0** (item 0, carrying both the parameterised globals and the convert tail that stops encoding) … both are additive … item 8 cannot land in the core while ocp_tessellate still base64s internally" (requs.md:599).

**Assessment.** Two defects. First, "both are additive" is false for this half as written: if `export_three_cad_viewer_js` stops encoding, its output format changes and every external user of the documented function breaks — inside a release whose whole justification is being additive so the `<3.5.0` ceiling is the only coordination needed. Second, "item 8 cannot land in the core while ocp_tessellate still base64s internally" is not true: the core's two walks replace `show.py:537`, which is ocp_vscode's call, and never touch the exporter — the only genuine step-1 prerequisite from item 8's side is that `numpy_to_buffer_json` stays importable for the byte-identity test, which deprecation already guarantees. Change: 3.5.0 keeps `export_three_cad_viewer_js`'s output byte-stable (internally it may keep calling the deprecated encoder, or gain an opt-in codec parameter defaulting to today's format), item 8's "both have to stop" becomes "the show-path call stops; the exporter keeps its documented format", and step 1's rationale sentence is corrected to the true dependency (the 3.5.0 floor exists so the matrix row is declarable).

### F6 (medium). "Shed questionary outright" is wrong — questionary belongs to the VS Code client's Comms, which stays

**What the code does.** `ocp_vscode/comms.py:24` imports questionary at module scope, and `comms.py:324-327` uses it as the interactive port picker when multiple viewers are found from a plain terminal; the Jupyter path beside it already has a questionary-free fallback (`comms.py:320-322`, plain `input()`). flask/flask_sock/pyperclip are genuinely standalone-only (`standalone.py:26-28,34`) and click is `__main__`-only (`__main__.py:18`), so the rest of the drop list is clean. Separately, `requests` is declared (`vscode-ocp-cad-viewer/pyproject.toml:31`) but imported by no module in the package (grep over `ocp_vscode/*.py` finds nothing).

**What the plan says.** "Printing lets ocp_vscode shed flask, flask_sock, click, questionary and pyperclip outright" (requs.md:583, repeated at :603); the 2.2 MB host-only list at requs.md:498 includes `requests`, which then never appears in the drop list.

**Assessment.** Dropping questionary from dependencies while `comms.py:24` still imports it makes `import ocp_vscode` raise — loudly and immediately, so this is a first-test find rather than a field failure, but the plan's causality ("printing lets ocp_vscode shed …") is wrong for this one package: shedding questionary is a small code change in the Comms that stays, not a consequence of the standalone leaving. Change: item 14 replaces the `comms.py:324` picker with the existing `input()` fallback (or keeps questionary deliberately), and `requests` — declared, unused, already counted in the plan's own 2.2 MB — joins the drop list.

### F7 (medium). Between step 2 and step 5 the golden master exists twice under active maintenance, and nobody is named to keep the copies converged

**What the code does.** `show.py` is 1745 lines with real users (requs.md:612 states it; the file confirms the scale), released as ocp_vscode 4.x, and ocp_vscode continues shipping user-facing fixes on it while the moved copy in `ocp_viewer_core` evolves from step 2 until ocp_vscode re-exports at step 5.

**What the plan says.** "no branch ever consumed" (requs.md:612); "the re-export is what protects it - no user's import changes, whatever moves underneath" (requs.md:612). Nothing about the window in which both copies are live.

**Assessment.** The re-export protects users only at step 5; during the window, any 4.x bugfix must be replayed into the core or the step-5 swap silently reverts it — a fork with drift, in the package whose behaviour is declared the golden master. Change: one sentence in the order of work declaring ocp_vscode 4.x fix-frozen for the window (critical fixes only, each mirrored into the core the same day), which is also the honest cost of the window being three steps long.

### F9 (minor). The step-5 and step-6 releases need their version numbers written down, because two mechanisms depend on them being majors

**What the code does.** jupyter-cadquery pins `ocp_vscode~=4.0.1` (`jupyter-cadquery/pyproject.toml:33`), which admits only 4.0.x; the extension enforces wheel/extension version equality with a warning-and-offer (`src/extension.ts:60-80`); the extension's install templates track its own version (`package.json:556-578`); Studio's runtime pins `ocp_vscode==4.0.1` exactly (`runtime/pyproject.toml:9`).

**What the plan says.** The matrix (requs.md:531-537) gives versions for the core, tessellate and (via item 11, requs.md:578) three-cad-viewer 5.1.0 — but no version for the step-5 ocp_vscode release or the step-6 cad-viewer-widget release.

**Assessment.** Step 5 removes an entry point, deletes dependencies and deletes documented behaviour — a major by any reading, and the pins above only protect existing users if it *is* one (any 4.0.x-compatible number would be pulled into jcq environments and break them). Change: state ocp_vscode 5.0.0 for step 5 and the widget's major/minor for step 6 in the matrix or the order of work, one line.

### F10 (minor). Who ships the renderer to pip-only users, and the miscount in "the other three read the wheel at runtime"

**What the code does.** Today the ocp_vscode wheel vendors the renderer: `ocp_vscode/static/js/three-cad-viewer.esm.js` (plus `comms.js` and `logo.js`), shipped via package-data (`vscode-ocp-cad-viewer/pyproject.toml:55-61`) — that is how a pip-only standalone user gets three-cad-viewer, which exists on npm but not on PyPI. The extension's webview is bundled at build time from node_modules, and the widget builds a labextension from npm — neither reads the Python wheel at runtime.

**What the plan says.** "Dual-publish … we build from `node_modules` at build time, the other three read the wheel at runtime" (requs.md:578), with three-cad-viewer as a peer dependency whose floor "fails at resolution rather than at runtime" (requs.md:578).

**Assessment.** Two gaps. The count: of the hosts, plausibly only `ocp_viewer` reads the wheel at runtime — the extension and the widget consume npm at build time and jcq sits above the widget. The substance: peer-dependency resolution protects npm consumers only; the wheel-reading host gets its renderer as a vendored file inside somebody's wheel, and the plan does not say whose (core's wheel or ocp_viewer's) nor how the vendored copy is held to the same 5.1 floor — drift between the wheel's vendored renderer and the npm peer floor would be invisible until runtime. Change: item 11 states which wheel vendors the three-cad-viewer dist and adds a build-time assertion that the vendored version satisfies the peer floor.

### F11 (minor). Loose ends of the standalone's migration surface: `--create_configfile`, `~/.ocpvscode_standalone`, and docs/standalone.md

**What the code does.** `--create_configfile` writes the standalone's YAML settings to `~/.ocpvscode_standalone` (`__main__.py:364-368`; `CONFIG_FILE` in `standalone.py`), and `README.md:130` points at `docs/standalone.md` for "the full CLI reference and how to run it in Docker".

**What the plan says.** Item 12 moves the standalone wholesale; the Open paragraph (requs.md:610) lists build123d docs ownership but not the standalone's own documentation; nothing says whether `ocp_viewer` reads the existing `~/.ocpvscode_standalone` or starts fresh.

**Assessment.** Small, but each is a user-visible seam: a migrating user's saved settings should survive (read the old path as fallback, or document the rename), and the Docker/CLI documentation must move to the new package's repository — Docker images are exactly the place where `python -m ocp_vscode` is baked in and the stderr-plus-non-zero decision (requs.md:583, which is the right decision) will surface. Change: one clause in item 12 for the settings-file fallback, and add the standalone docs to the Open list beside the build123d docs.

## Where the plan is sound

Verified and worth stating for the go decision. The registry names are free: `pypi.org/pypi/ocp-viewer/json`, `pypi.org/pypi/ocp-viewer-core/json` and `registry.npmjs.org/ocp-viewer-core` all return 404 (2026-08-08). The irreversibility ordering is right: everything through step 4 is additive or new-name (tessellate 3.5.0 deprecates rather than deletes — `numpy_to_json`'s consumers at `ocp_vscode/animation.py:25` and `jupyter_cadquery/tools.py:23` keep working; three-cad-viewer 5.1.0 keeps `decodeInstancedFormat` as the composition; the core and the standalone are new names), and the destructive step 5 comes after two adoptions would have exposed a wrong interface. The version matrix is internally consistent with its own rule (floor at major.minor, ceiling at next minor, patch free) and resolvable in the target state; the only resolution defect is the transitional one in F2. The no-OCP-provider rule matches reality exactly: `ocp-tessellate/pyproject.toml:29` declares `webcolors`, `numpy`, `cachetools`, `imagesize` and nothing else, and no package in the chain declares a provider today. The separate-package decision for the core is carried by a receipt this repository can produce (the port-3939 cross-talk bug), and moving the standalone out is what makes the dependency drop possible at all — `flask`/`flask_sock`/`pyperclip` are confirmed standalone-only. Item 13's "242 lines today" is exact (`wc -l kernel/build123d_studio/__init__.py` = 242). The stderr-plus-non-zero-exit decision for the retired entry point is right and grounded — `README.md:130` documents scripted and Docker use, which is precisely the consumer a stdout-and-zero notice would silently strand. The six-step order is buildable at every step once F1, F2 and F5's corrections are applied; no step depends on an artifact a later step produces.
