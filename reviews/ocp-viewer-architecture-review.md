# Architecture and design review: the `ocp-viewer` restructuring concept (requs.md §7)

Reviewed against the source of all five projects on this machine: `vscode-ocp-cad-viewer`, `cad-viewer-widget`, `jupyter-cadquery`, `three-cad-viewer`, and this repository. Every claim below cites the file and line it was read from; anything that could not be established from source is under *Could not verify*. Paths are repo-relative with the repo named once per finding; this repository's paths are given as `kernel/…`, `sidecar/…`, `src/…`.

## Verdict

The concept is sound and unusually well grounded: the shared/per-host table matches the real call graphs, the coupling it proposes to cut is import-time environment-variable rewiring rather than deep logic entanglement, and the two hardest claims — that a `Comms` interface already exists implicitly, and that `status()` is a value handed over rather than a question asked — are both confirmed by the code, the second even more strongly than the plan states (no host does a live round trip for status; all four answer from a cache). It is a go. Five things should be amended before Phase 1 starts, each tied to a finding below: (1) item 6's inventory of module globals is incomplete, and one set of per-show global writes lands in `ocp_tessellate`, outside `ocp-viewer`'s reach — the "two viewers in one process" claim does not hold until that is settled; (2) item 10's function census misses the largest single block of policy in `viewer.html`, the anonymous message listener whose `ui` dispatch is the whole of apply-config — without it, `set_defaults`/`set_viewer_config` work in one host only; (3) the config key table needs an *owner* column, because the `cad_width`/`height`/`theme` branches encode a real capability difference between hosts that injection moves but does not dissolve; (4) item 9's conformance kit must specify the Comms *failure* contract, because today's offline behavior differs per host and one path poisons its own wire format; (5) item 2's live status object must exclude selection keys, or it reintroduces a stale-re-measurement bug this repository deliberately fixed. None of these change the architecture; all of them change what Phase 0/1 has to write down.

## Findings

### 1. The shared/per-host split is in the right place, and the entanglement to cut is shallow — import-time rewiring, not logic

**What the code does.** Host selection today is one environment variable checked at import time in three modules: `ocp_vscode/show.py:66-78` swaps the entire comms import (`jupyter_cadquery.comms` vs `ocp_vscode.comms`) on `JUPYTER_CADQUERY == "1"` and freezes `is_jupyter_cadquery` as a module constant; `ocp_vscode/config.py:22-32` and `ocp_vscode/backend.py:42-47` do the same. jupyter-cadquery sets that variable as its first act (`jupyter_cadquery/__init__.py:20`) and then imports `_show`/`_show_object` (`jupyter_cadquery/show.py:25`) and half of `ocp_vscode.config` (`jupyter_cadquery/__init__.py:35-46`). Crucially, `jupyter_cadquery/comms.py` already implements the exact same four-function surface — `send_data` (:80), `send_command` (:124), `send_backend` (:172), `send_config` (:226) — with signatures deliberately matching `ocp_vscode/comms.py:226-247`, and its docstrings say which ocp_vscode function calls each. build123d Studio does the same one level down: it injects its transport by calling `_convert` directly and replacing only delivery (`kernel/build123d_studio/__init__.py:118-122`, `_deliver` at :92-115, `kernel/build123d_studio/transport.py:65-80`).

**What the plan says.** "`_show`, the show family, tessellation, config semantics, the measurement backend and both codecs" shared; "a `Comms`, a settings source, about eight lines of re-export" per host (requs.md:508).

**Assessment.** Confirmed in direction, with two qualifications. First, "tessellation" as a shared item mostly already *is* shared: the actual tessellator is `ocp_tessellate` (`tessellate_group`, `to_ocpgroup` imported at `ocp_vscode/show.py:38-44`), a distribution every host installs today; what moves into `ocp-viewer` is the ~260-line config-merging wrapper `_tessellate` (`show.py:228-491`). Second, the base64 codec the plan wants to own does not live in ocp_vscode either — `numpy_to_buffer_json` is `ocp-tessellate/ocp_tessellate/utils.py:233-256` — so item 8's "two shared walks" put codec ownership across a package boundary the plan never names (see finding 6). The measurement backend is confirmed shareable: its geometry (`load_model` at `ocp_vscode/backend.py:146-194`, `ocp_vscode/measure.py`) is host-free, its four `is_jupyter_cadquery` branches (`backend.py:200,211,221,232`) are only about *where the answer goes*, and this repository already proves the subclass-and-return shape works (`sidecar/measure.py:28-58`). The per-host column is also confirmed: four genuinely different settings sources exist (VS Code settings via `src/controller.ts:76`; `~/.ocpvscode_standalone` YAML at `ocp_vscode/standalone.py:36,252-262`; `get_user_defaults()` in `jupyter_cadquery/comms.py:145`; this repository's settings). One nuance: the command *vocabulary* the four Comms carry — `status`, `config`, `screenshot`, `set_relative_time`, `clear`, `ui`, `animation`, `backend_response` (dispatched at `src/controller.ts:206-253` in the extension, `ocp_vscode/standalone.py:358-467`, `viewer.html:692-922`) — is itself shared semantics and must be specified in `ocp-viewer` as the interface each Comms implements, even though every transport is per-host. The plan names only `status()`; the rest should be named with it.

### 2. The plan undercounts the round trips it is about to remove: a default `show()` in a VS Code host makes six blocking command connections, not two

**What the code does.** Every `_send` opens a *fresh* websocket connection (`with connect(f"{CMD_URL}:{port}", close_timeout=0.05)`, `ocp_vscode/comms.py:159-161`) and, for commands, blocks on the reply (:169-174). A default `show()` (no `timeit=`, camera not kept or model changed) reaches `send_command` this many times: `preset("timeit", …)` in `_show` (`show.py:855`) → `get_default` → `get_defaults` → `workspace_config` → connection 1; the same `preset` again in `_convert` (`show.py:504`) → connection 2 (the earlier result was never written back into `kwargs`); `combined_config` in `_tessellate` (`show.py:241`) → `workspace_config` + `status` (`config.py:742-743`) → connections 3 and 4; `preset("timeit", …)` a third time (`show.py:288`) → connection 5; `get_changed_config` (`show.py:294` → `config.py:760-767`) → connection 6; `get_defaults` for the clip-insight reset (`show.py:462`) → conditional connection 7. Then `send_data` (`show.py:921`) and `send_backend` (:927) are two more. In jupyter-cadquery those six are cheap local reads (`jupyter_cadquery/comms.py:144-166` answers `config` from a settings file and `status` from traitlets); in build123d Studio they are six doomed connects to the isolation port that the sidecar refuses by design (`sidecar/kernel.py:562-575`, `kernel/build123d_studio/__init__.py:60-74`).

**What the plan says.** The review brief's claim under test was "status/workspace_config are each a blocking send_command so every show is two round trips".

**Assessment.** True in kind, undercounted by a factor of three: the two *distinct* commands are fetched up to six times because `preset`, `get_changed_config` and `get_defaults` each re-fetch `workspace_config` rather than reusing a snapshot. This is the strongest quantitative argument for item 7's shape — a `Session` that fetches the settings value and the status value once per show and passes them down (`combined(status)` as a pure merge) removes four of the six connections as a side effect of the design, before any deliberate optimization. It should be stated as such in the plan, and the conformance kit should assert the count (one settings read, one status read per show).

### 3. Item 6's `Session` matches the code's structure, but the module-global inventory is larger than "DEFAULTS and the push accumulator" — and one set of globals is outside `ocp-viewer`'s reach

**What the code does.** The family is exactly as described: one entry point `_show` (`ocp_vscode/show.py:799-927`), argument adapters (`show` :573-796, `show_object` :945-1174, `show_objects` :1343-1560, `show_all` :1571-1717), and an accumulator (`OBJECTS` at :116-123, fed by `push_object` :1276-1340 and `_show_object` :1199-1273, reset by `reset_show` :930-941). But the mutable module state a `Session` must absorb is: `OBJECTS` (:116), `LAST_CALL` (:125, written at :800,910-912,1595-1601), `DEFAULTS` (`config.py:295-305`, written by `set_defaults` :647 and reassigned by `reset_defaults` :786), `COLORMAP` (`colors.py:40-59`, read per show at `show.py:874`), `LAST_BBOX` (`utils.py:94-103`, the camera-keep heuristic at `show.py:448`), `LAST_PATHS` (`utils.py:172-196`), the once-per-session warning flags (`utils.py:54-55`), and the comms globals `CMD_PORT`/`CMD_URL`/`INIT_DONE` (`comms.py:50-53`) which become each Comms's own state. On top of those, `_tessellate` writes **another package's** module globals on every show: `oc.FACE_COLOR`, `oc.THICK_EDGE_COLOR`, `oc.VERTEX_COLOR` (`show.py:263-283` assign into `ocp_tessellate.convert`).

**What the plan says.** "It also turns today's module globals, `DEFAULTS` and the push accumulator, into instance state, which is what makes two viewers in one process representable and the whole of it testable" (requs.md:533).

**Assessment.** The `Session` is the right unit — nothing in the family is host-specific once Comms and Config are injected (the one branch inside `_show`, at :923-927, is transport and return-value shape; see finding 4). But "two viewers in one process representable" is overstated as written: with two Sessions live, the `oc.FACE_COLOR` writes race between them per show, and `ocp_tessellate` is not in the plan's scope. Either those three parameters become arguments through `to_ocpgroup`/`tessellate_group` (an upstream API change the plan should name as a prerequisite of the two-session property), or the plan should state that per-session isolation covers everything *except* the tessellation default colors. Also missing from the family list: `remove_object` (:1177-1196), `save_screenshot` (:1720-1745, a command plus filesystem polling), `set_viewer_config`/`reset_defaults` (`config.py:334-426,770-797`), and the `Animation` class (`ocp_vscode/animation.py:26,131,145` — it calls `send_data`/`send_command` directly and is part of the wire vocabulary). They are all Session-shaped; they just need to be on the list so none is left importing a module-level comms.

### 4. "Inject, do not identify": the census, one branch class injection does not dissolve, and two host-naming sites the plan misses

**What the code does, branch by branch.**

- **Import rewiring** — `show.py:66-78`, `config.py:22-32`, `backend.py:42-47`, keyed on the `JUPYTER_CADQUERY` env var. Pure plumbing; injection removes it outright.
- **Transport tail** — `show.py:920-927`: jcq's `send_backend` takes `jcv_id=viewer.widget.id` and `_show` *returns the viewer*; VS Code's takes `port=` and returns `None`. Injection dissolves the branch only if the Comms contract says `send_data` returns an opaque viewer handle that `send_backend` accepts and `Session.show` returns. That is a real interface decision, not a deletion — the plan should write it down.
- **Capability branches** — `show.py:351-363` excludes `cad_width`/`height`/`theme` from the config in VS Code because the panel owns them, and :365-375 prints "Setting cad_width cannot be set, it is determined by the VSCode panel size" (a host named in a shared-code string). `config.py:645` accepts `viewer`/`cad_width`/`height` as defaults only in jcq. This is a genuine behavioral difference between hosts — who owns the canvas geometry — and injection *moves* it, it does not dissolve it. The right home is the item 3 table: an ownership column (host-owned vs code-settable per host class), from which both the exclusion and the message are derived. Without that column the branch reappears inside each host with a different spelling.
- **`is_pytest()`** — nine sites: definition and port short-circuit (`comms.py:84-85,112`), canned data at `config.py:678` (`status` returns `{}`) and :701-707 (`workspace_config` returns a canned dict), and return-shape switches at `show.py:535` (`_convert` returns raw tuples instead of encoded data), :917, :1709, :1715. All genuinely dissolved by item 9's loopback Comms plus an injected settings source; the `show.py:535` site is worth noting because it means the *codec choice* is currently also test-gated, which item 8 fixes for free.
- **`port=`/`viewer=` pairs** — `config.py:389-390` (`set_viewer_config`), :511-513 (`set_defaults`), :675 (`status`), :698 (`workspace_config`), :735 (`combined_config`); threaded through kwargs at `show.py:238-239`; 10 `port=None` and 5 `viewer=None` defaults in `config.py` alone. All become Comms construction state.
- **Missed by the plan's census, and by its own success criterion:** `show.py:1634` excludes objects whose class string contains `"cad_viewer_widget.widget"` from `show_all` — a host named inside would-be-shared code *as a string*, which the package-boundary-makes-it-an-import-error argument (requs.md:502) cannot catch; only the conformance kit or review can. Likewise the ipython/Jupyter environment sniffing in `comms.py:40,320,354-373` (`get_ipython`, `ZMQInteractiveShell`, the `.ocpvscode` state file) is VS-Code-host machinery that must move into that host's Comms, not survive in the core.

**What the plan says.** "Delete every `port=`/`viewer=` pair and every `is_jupyter_cadquery` and `is_pytest()` branch. The success criterion is that no host is nameable inside `ocp_viewer`" (requs.md:534).

**Assessment.** Right, with the two amendments above: the capability branches become table rows rather than deletions, and the success criterion needs "no host is nameable" to include strings and environment sniffing, which only item 9's kit can enforce.

### 5. `Config` over a host settings source and `combined(status)` as a pure merge: supported by the real precedence — and the plan's own transport paragraph contains one factual error that *strengthens* its conclusion

**What the code does.** The real precedence in `combined_config` (`config.py:735-757`) is: workspace config, overlaid by `workspace_filter(status)` unless `_splash`, overlaid by `DEFAULTS`; then `_tessellate` overlays explicit kwargs (`show.py:365-381`). Both normalizations are pure: status's collapse reverse-mapping (`config.py:687-693`) and workspace's string→enum mapping (:712-727). A second merge exists that skips status entirely (`get_changed_config`, :760-767) — trivially `combined({})`. As for where status *comes from*: the VS Code extension answers the `status` command from a cached copy of the webview's last status postMessage (`src/controller.ts:163-166` caches, :210-211 answers) — the webview is not consulted; the standalone answers from a dict accumulated from U-frames (`ocp_vscode/standalone.py:370-374`, fed at :435-439); cad-viewer-widget reads traitlets synchronously (`cad_viewer_widget/widget.py:2126-2160`, wrapped at `jupyter_cadquery/comms.py:157-166`); this repository has no path at all yet (`sidecar/modelsock.py:134-191` never sends). On failure, `_send` returns a dummy dict for *any* command (`comms.py:191-214`) — which puts a `Collapse` **enum** where `status()`'s consumers expect the wire value, the exact mismatch this repository filters warnings about (`kernel/build123d_studio/__init__.py:66-74` citing `config.py:688-693`); and if `_send` returns `None` (its outer exception path, `comms.py:218-223`), `send_command` crashes on `result.get` (`comms.py:236-242`).

**What the plan says.** "Ours is a reply frame on the model socket, the VS Code pair's is a `postMessage` round trip, the standalone's is its websocket, and cad-viewer-widget's can be a wrapper over traitlets… the shared core must not assume `status()` costs a round trip" (requs.md:511).

**Assessment.** The design is right and the code supports it — but "the VS Code pair's is a `postMessage` round trip" is refuted: it is a websocket hop to the extension answered synchronously from a cache. That makes the plan's own conclusion *stronger* than it claims: **no** host asks the frontend anything at status time; all four hand over remembered state, differing only in where the memory lives and how it is fed. The freshness caveat (requs.md:513) is therefore exactly right and should stay. What the plan does not yet define is the Comms *failure* contract: today one host raises (`kernel/build123d_studio/transport.py:31-43` `NotConnected`), one prints and returns fake data in-band (`comms.py:191-214`), one can crash (`comms.py:238`), and jcq returns `{}` for a missing sidecar (`jupyter_cadquery/comms.py:158-161`). `Config`/`Session` need one defined offline behavior, and item 9's kit needs a dead-Comms test — see recommendation 4.

### 6. Codecs (item 8): every specific claim verified; the dtype and alignment policy is currently written in three places, and codec ownership crosses into `ocp_tessellate`

**What the code does.** `_convert`'s tail (`ocp_vscode/show.py:534-545`): under pytest it returns raw tuples; otherwise it calls `numpy_to_buffer_json` (`ocp-tessellate/ocp_tessellate/utils.py:233-256` — ravel, then base64 into `{shape, dtype, buffer, codec:"b64"}`) and wraps `{data, type, config, count}`. Who depends on the base64 shape: three-cad-viewer's decoder (`src/utils/decode-instances.ts:76-91` `decodeBuffer` → `fromBase64` :61-73, plus a per-byte `charCodeAt` loop and a `buffer.slice` copy), this repository's `split_buffers` which exists solely to undo it (`kernel/build123d_studio/buffers.py:1-19` docstring, decode at :44-58), and cad-viewer-widget which passes the strings through untouched (`js/lib/widget.js:695-697`: "decodes the b64 buffers and instance refs natively (like ocp_vscode)"). The dormant binary encoder is exactly as claimed: `cad_viewer_widget/utils.py:61-84` walks the tree turning `np.ndarray` into `{shape, dtype, buffer: memoryview(...)}`, tagged on the trait at `cad_viewer_widget/widget.py:202`, against `ipywidgets~=8.1.5` (`pyproject.toml:25`) and `@jupyter-widgets/base ^6.0.10` (`js/package.json:41`) — and it never fires because `_convert` has already replaced every array with a base64 *string*, which fails the `isinstance(obj, np.ndarray)` test and passes through. Dtype policy today: the widget's `to_json` coerces `int32/int64/uint64 → uint32` at encode time (`utils.py:64-65`); `numpy_to_buffer_json` does not coerce at all; three-cad-viewer reinterprets `int32` as `Uint32Array` at decode (`decode-instances.ts:85-87`); this repository does the same reinterpretation in its own decoder (`src/viewer/rehydrate.js:13-18`) and adds an 8-byte alignment rule the encoder must honor (`buffers.py:26-31`, checked at `rehydrate.js:37-43`).

**What the plan says.** "`_convert` stops choosing an encoding… `to_json` and `to_binary` ship as two shared walks that a Comms picks between. ocp_vscode's wire stays byte-identical; ours loses an encode *and* a decode per show… this item does not *add* binary to the widget, it unblocks the binary the widget already wrote" (requs.md:535-537).

**Assessment.** Verified end to end at the source level (the ipywidgets runtime lift itself is in *Could not verify*, as the plan itself concedes). Two additions the plan needs. First, ownership: the byte-exact reference encoder lives in `ocp_tessellate`, not ocp_vscode — `to_json` must either call it or replace it, and if it replaces it, "byte-identical" needs a test pinned against `numpy_to_buffer_json`'s output, because two packages will then be able to drift. Second, the two walks must own the *whole* codec policy in one place: dtype coercion versus reinterpretation (currently decided differently in the widget encoder and the two decoders) and the alignment/padding rule (currently only in this repository's pair). `decode(encode(model))` as the invariant (requs.md:515) is the right test; it should explicitly cover dtype identity and view alignment.

### 7. The JS side: item 1 is verified in every detail; item 10's census misses the largest block of policy in `viewer.html`

**What the code does.** three-cad-viewer 5.0.2 (`package.json`): `decodeInstancedFormat` fuses decode and resolve (`src/utils/decode-instances.ts:223-232`), `EncodedBuffer` is `{shape, dtype, buffer, codec}` with `codec: "b64"` as a literal type (:21-26), `isEncodedBuffer` tests `codec === "b64"` (:113-122), `decodeBuffer` calls `fromBase64` unconditionally (:76-78), and the ref-resolution half (`resolveRefs`, :178-195) is duplicated in this repository as `resolveInstances` (`src/viewer/rehydrate.js:73-97`, ~25 lines — the brief's "23-line copy" is accurate to within the function braces) for exactly the stated reason (`rehydrate.js:66-72`: the library's path "base64-decodes every instance first and would throw on the typed arrays we already hold"). The split is called from one place (`src/core/viewer.ts:1434-1439`), so it is a clean seam. `viewer.html` (950 lines; `resources/viewer.html` and `ocp_vscode/templates/viewer.html` are byte-identical, and the standalone renders the same file with an injected `vscode` shim, `ocp_vscode/standalone.py:63-83,341-351`) has **16 named functions** plus two anonymous `function` handlers (18 `function` tokens; the plan says seventeen). Of the named ones, exactly the claimed five are host-specific: `send` (:187-192, `vscode.postMessage`), `debugLog` (:127-131, via `send`), `getSize` (:275-280, `window.inner*`), `normalizeWidth`/`normalizeHeight` (:263-273, hard-coded panel chrome). But the biggest policy block is in neither census: the anonymous message listener (:671-923) contains the `ui` dispatch (:765-910, ~145 lines mapping every config key to a viewer setter — the entire receiving half of `set_viewer_config`/`set_defaults`), the tree-state preservation logic the goals bullet at requs.md:490 names as the thing to understand and replicate (:692-746: capture old states, `_splash` zoom, explicit-states-vs-restore branching), and the animation branch (:911-922) with `addAnimationTrack` (:133-164).

**What the plan says.** "Extract the policy from `viewer.html`: `showViewer`, `render`, `getStates`, `walk`, `getDisplayOptions`, `preset`, `nc`. Of its seventeen functions only `getSize`, `normalizeWidth`, `normalizeHeight`, `send` and `debugLog` are host-specific" (requs.md:542).

**Assessment.** The five-host-specific claim holds for named functions, and the extraction list is right as far as it goes — but incomplete. If the `ui` dispatch, the state-restoration block and the animation application are not named in item 10, they stay in `viewer.html` and `set_defaults`/`set_viewer_config`/tree-preservation work only in the VS Code pair; this repository's port (`src/viewer/viewer.js`) demonstrates the gap concretely — it ported `getDisplayOptions`/`render`-equivalents (:118-156, 197-231) but has no `ui` dispatch and no state restoration, which is exactly why item 13 lists `set_defaults`, `show_clear` and tree-state preservation as things Studio gains. Extract them as named policy functions (e.g. `applyConfig(viewer, config)`, `restoreStates(viewer, oldStates, newStates, explicit)`, `applyAnimation(viewer, tracks, speed)`) with `send` injected. The "per host: canvas, size, lifecycle, receiving half of Comms" column is confirmed by this repository's viewer.js, whose size logic deliberately diverges for good local reasons (measured `reservedHeight` at `viewer.js:98-112` versus the hard-coded 65 px at `viewer.html:271-273`) — size *should* stay per host.

### 8. The config key table (item 3) is even more justified than the plan claims — but only if it is generated into both languages

**What the code does.** The five lists exist as stated (`ocp_vscode/config.py:164-203, 205-236, 238-249, 251, 253-293`) and the hand-maintenance failure mode is already live *inside* them: `ambient_intensity`, `direct_intensity`, `metalness` and `roughness` appear both in `CONFIG_UI_KEYS` (:165,179,182,184) and again in the additions that build `CONFIG_WORKSPACE_KEYS` (:223,232,233,235). `toCamelCase` plus the `optionKeyOverrides` escape hatch exists at both `viewer.html` call sites (:360-365 with the loops at :374-381 and :400-407), duplicated in this repository (`src/viewer/viewer.js:20-49`). Beyond the plan's count, the same key classification is hand-kept in at least four more places: cad-viewer-widget's `display_args`/`viewer_args` whitelists (`cad_viewer_widget/utils.py:125-139, 142-208`), its ~60 synced traitlets (`widget.py:150+`), and the widget's own option assembly (`js/lib/widget.js:341+`).

**What the plan says.** "It replaces five hand-kept overlapping lists … and `viewer.html`'s `toCamelCase`, whose failure mode is silence" (requs.md:527).

**Assessment.** Correct and undersold — roughly a dozen key collections across four repositories encode the same table today. The consequence the plan should draw explicitly: the table must be a *generated* artifact (Python constants and a JS module emitted from one source in `ocp-viewer`, plus, in Phase 5, the widget's trait filters), otherwise it becomes the thirteenth hand-kept list. The lifetime column is right; per finding 4 it needs an ownership column too.

### 9. Item 2's "live status object" conflicts with a deliberate decision in this repository's viewer, and the plan does not resolve it

**What the code does.** ocp_vscode's `nc()` keeps a running `message` object that accumulates every change ever reported and re-sends the whole snapshot (`viewer.html:63`, :238-247, :258-260, and `render()` refreshes it at :602-623). This repository's `notify()` explicitly refuses that shape: it sends only the delta, because "a stale selectedShapeIDs rides along with every unrelated change and the backend re-measures a selection the user made minutes ago" (`src/viewer/viewer.js:169-185`) — and the measurement path is live on those very frames (`sidecar/main.py:233`, `on_viewer_changes` :568-578). The standalone shows the accumulate-server-side alternative: deltas arrive, the server folds them into `self.status` (`ocp_vscode/standalone.py:435-439`) and answers `status` from it (:370-374) — but it also forwards each delta batch to the backend (:440), which is the same stale-selection exposure the Studio comment describes.

**What the plan says.** "have the frontend hold a live status object fed by three-cad-viewer's change callback, answering a `status` command from it" (requs.md:526).

**Assessment.** The reply hop itself is right and small — `modelsock.py` only reads (:134-191), and the delta channel already exists. But whichever side holds the accumulated object (frontend per item 2, or sidecar like the standalone), the accumulation must exclude selection/tool keys (`selectedShapeIDs`, `activeTool`) from what feeds measurement, or the fix at `viewer.js:169-177` is undone. The shared status contract (finding 5) should therefore partition keys: state keys (accumulate, report in `status`) versus event keys (deliver once, never replay) — a column the item 3 table can carry.

### 10. What the plan does not address

- **The logo has five copies and no assigned home.** `src/logo.ts` (extension), `ocp_vscode/static/js/logo.js` (standalone) and this repository's `src/viewer/logo.js` are byte-identical 261-line files (verified by diff); `ocp_vscode/backend_logo.py` (44 lines) is the Python/BRep copy loaded into the backend at start (`backend.py:101`, `standalone.py:327`); `jupyter_cadquery/logo.py` is a fifth, a one-line JSON string. The goals bullet (requs.md:492) parks the Studio measurability question here precisely because "which logo, whose copy of it, and who ships it" belongs to this group — but no numbered item then answers it. It should be an `ocp-viewer` asset: one source, the JS and Python forms generated or shipped by the dual-publish (item 11), consumed by item 13's `backend_logo.py`-through-the-shared-backend.
- **`ocp_tessellate`'s place in the versioning contract.** Item 11's peer floor covers three-cad-viewer only, but `ocp-viewer` will depend on `ocp_tessellate` for tessellation *and* (per finding 6) for byte-identical encoding, and hosts pin it independently today. The format-version-is-the-schema-version decision (requs.md:552) makes `ocp_tessellate` the de facto owner of that schema; the contract should say which package pins it and with what floor.
- **Animation** is absent from the shared column, the Session family and the JS extraction, yet it is a cross-host feature with wire presence in three hosts (`ocp_vscode/animation.py:131,145`; `viewer.html:911-922`; the widget's `tracks` trait at `cad_viewer_widget/widget.py:214` and jcq status passthrough).
- **The Comms failure contract** (finding 5): the current per-host behaviors range from a typed exception (`transport.py:31-43`) to in-band fake data (`comms.py:191-214`) to a latent `AttributeError` (`comms.py:236-242`). Item 9 should include a dead-Comms conformance case.
- **`show_all`'s filter semantics diverge between hosts and the plan picks neither.** ocp_vscode admits any `list`/`tuple`/`dict` (`show.py:1662`); this repository deliberately requires the contents to be drawable, because a list of floats once produced a geometry-free model that hung the viewer (`kernel/build123d_studio/__init__.py:167-204`, with the second and third defenses at :104-106 and `src/viewer/viewer.js:322-328`). "Today's behaviour is the golden master" (requs.md:558) would, applied literally, regress the Studio fix; the shared `show_all` should adopt the recursive check and the plan should say so.
- **Nothing in the plan is over-engineered.** The two candidates were checked: the separate distribution is carried by a concrete receipt (the cross-talk bug, `sidecar/kernel.py:562-575`, requs.md:554), and the conformance kit is the only mechanism that can catch the string-shaped host references a package boundary cannot (finding 4, `show.py:1634`). Item 2 reuses an existing channel rather than adding one (`modelsock.py`, `main.py:233`). The versioning contract (major.minor floor, per-host patch) matches the observed pins: three-cad-viewer 5.0.2 upstream, 5.0.2 in the widget (`js/package.json:44`) and extension (`package.json:793`), 5.0.0 here (`package.json:32`); jcq pins `cad-viewer-widget~=4.0.0` and `ocp_vscode~=4.0.1` (`pyproject.toml:30,33`).

## Design qualities

**Reusability.** High, and demonstrated rather than hoped: the Comms interface already has two independent implementations with matching signatures (`ocp_vscode/comms.py` vs `jupyter_cadquery/comms.py`, finding 1), and the measurement backend already has its second consumer via subclassing (`sidecar/measure.py:28-58`). Extraction here is naming what exists.

**Simplicity.** The plan removes mechanisms rather than adding them: one env-var import rewiring across three modules, ~21 `is_jupyter_cadquery` mentions and 9 `is_pytest` sites (finding 4), six redundant config fetches per show (finding 2), and one whole file whose job is undoing an encoding (`kernel/build123d_studio/buffers.py`). The additions — Session, Config, two codec walks, a table — each replace more than they cost. The main simplicity risk is the table growing columns (lifetime, owner, status-reporting, key-class per findings 4/8/9); that is still one artifact where today there are a dozen.

**Encapsulation.** The package boundary argument is sound and receipted (`sidecar/kernel.py:562-575`), but as finding 4 shows, imports are not the only leak: strings (`show.py:1634`), user-facing messages (`show.py:368`), and environment sniffing (`comms.py:40,320`) name hosts too. The kit, not the boundary, is the enforcement for those — the plan says this (requs.md:502) and it is right.

**Robustness.** The weakest area of the current code and the least specified part of the plan: in-band dummy data that violates its own wire contract (`comms.py:191-214`), a crash path in `send_command` (`comms.py:236-242`), silent option loss via `toCamelCase` (finding 8), and a viewer that hangs on a geometry-free model (guarded only in this repository, finding 10). The conformance kit is the right instrument; it needs failure cases, not just loopback happy paths.

**Well-definedness of interfaces.** `Comms` is nearly defined by the existing four functions plus `status()`; the open points this review adds are the `send_data` return handle (finding 4), the failure contract (finding 5), the command vocabulary (finding 1), and the status key partition (finding 9). `Config`'s merge is definable today from `config.py:735-767` plus the two normalizations.

**Architectural coherence.** The adoption order (Studio → ocp_vscode both → jcq) matches the measured dependency structure — jcq imports from both ocp_vscode and the widget (`jupyter_cadquery/__init__.py:22-57`) so it must move last; the standalone as first thin JS host is credible because it already runs the exact shared `viewer.html` behind a five-line shim (`standalone.py:63-83`). Deriving the interface from the other three hosts' call sites before implementing ours (requs.md:558) is the right discipline for an atypical first adopter.

**Performance.** Per show today in the VS Code pair, the model data is copied or transformed roughly eight times after tessellation: base64 encode (`ocp_tessellate/utils.py:243`), `orjson.dumps` (`comms.py:145`), `message.toString()` and `substring(2)` (`src/controller.ts:204,207`), the `postMessage` string serialization (:225), `JSON.parse` (`viewer.html:689`), `atob` plus a per-byte `charCodeAt` loop (`decode-instances.ts:61-73`), and a `buffer.slice` (:78-81) — two of these are per-byte JavaScript loops. This repository's path is already down to one encode plus one decode (`buffers.py`), which item 8 reduces to approximately zero copies (typed-array views over the frame, `rehydrate.js:31-45`); the widget path drops its encode+decode pair when item 8 unblocks its dormant binary encoder. Round trips: finding 2 (six blocking connects per show today in the VS Code pair, each a fresh TCP+WS handshake, `comms.py:159-161`; two under the Session design). Startup: `import ocp_vscode` executes star-imports of the entire package including OCP-heavy `show` (`ocp_vscode/__init__.py:23-31`); the plan's import-free `__init__` for `ocp-viewer` (item 5) is structurally necessary, and this repository's sidecar is the measured proof of what a top-level OCP import costs a host that must not pay it (requs.md:532; `sidecar/measure_service.py:1-31`).
